# Попередня архітектура та GoF

## Принцип

Один GitHub-репозиторій (монорепозиторій) із `frontend/` (React + TypeScript) та `backend/` (Express + TypeScript). Frontend звертається до backend через REST API; дані зберігаються в PostgreSQL з використанням Prisma. Backend — модульний моноліт із модулями `books`, `readers`, `rentals`, `reports`, `auth`, `settings`. Всередині модуля: controller → service → repository/data access. При зміні БД бізнес-логіка не повинна змішуватися з Express-контролерами.

## Реалізований модуль books

`src/modules/books/` реалізує ланцюжок `books.routes → BooksController → BooksService → BooksRepository`. Контролер перевіряє body/query/UUID Zod-схемами й формує HTTP-відповіді. Сервіс визначає 404/409, правила архівування, пагінаційні метадані та серіалізацію сум із двома десятковими знаками. `PrismaBooksRepository` реалізує контракт доступу до даних: фільтри PostgreSQL без урахування регістру, стабільне сортування, пагінацію та групування примірників за книгою/статусом без завантаження їхніх списків у каталозі.

Repository перетворює лише дозволені грошові рядки на `Prisma.Decimal`. PATCH і DELETE використовують умовний `updateMany` з `archivedAt: null`, тому конкурентне архівування не дозволяє редагувати вже архівований запис. Повторне архівування та PATCH архівованої книги дають 409; DELETE змінює тільки `Book.archivedAt`, зберігає примірники й історію. Відновлення буде окремою задачею. Каталог типово приховує архівні книги; `includeArchived=true` включає їх, а отримання за UUID залишається доступним.

`createApp` приймає підмінений `BooksRepository` для HTTP-тестів. Без підміни repository ліниво завантажує наявний `src/lib/prisma.ts`; додаткових Prisma Client чи пулів немає. Health і звичайні автоматизовані тести не потребують БД. `scripts/check-books.ts` використовує цей самий repository із транзакційним клієнтом локальної БД: HTTP CRUD перевіряється з відкатом та порівнянням усіх дев'яти таблиць.

До реалізації автентифікації `developmentLoopbackOnly` дозволяє POST/PATCH/DELETE лише в development із фактичної loopback TCP-адреси. У production/test вони дають 403 до розбору JSON. `trust proxy` вимкнено, HTTP-заголовки не визначають права. GET тимчасово відкриті. Це обмеження не замінює автентифікацію/RBAC; development-сервер не призначений для публікації через локальний проксі чи тунель. Обов'язкову перевірку ролей перед публічним деплоєм реалізуємо окремо.

`ApiError` і Zod-помилки обробляє спільний error middleware у форматі `{ error: { code, message } }`; непередбачені помилки повертають безпечний 500. Контракт API, приклади й команди перевірки наведені в README. Нових GoF-патернів модуль не вводить.

## Реалізований модуль book-copies

Окремий `src/modules/book-copies/` має `BookCopiesController → BookCopiesService → BookCopiesRepository`. Вкладений router `/api/books/:bookId/copies` підключено до API перед router Books, із `mergeParams` для UUID книги та власними строгими Zod-схемами params/query/body. Використовується наявний `developmentLoopbackOnly` перед JSON parser. `createApp` приймає окремий підмінений repository; за замовчуванням `PrismaBookCopiesRepository` ліниво завантажує спільний Prisma Client.

Сервіс визначає бізнес-обмеження всередині `repository.transaction`: 404 для відсутніх/чужих записів, заборона запису архівованої книги, лише `AVAILABLE`/`MAINTENANCE` без активного Rental для зміни статусу, а для DELETE — лише `AVAILABLE` без будь-якої історії. Інвентарний номер редагується незалежно від статусу, без зміни історії. Repository передає сервісу транзакційний контракт `BookCopiesWriteRepository`; результат PATCH читається в тій самій транзакції.

Записи використовують PostgreSQL `ReadCommitted`, спочатку `SELECT Book ... FOR SHARE NOWAIT`, потім `SELECT BookCopy ... FOR UPDATE NOWAIT`. SHARE захищає від архівування Books, дозволяючи обробляти різні примірники паралельно. UPDATE захищає примірник від зміни/видалення та конфліктує з key-share блокуванням FK під час вставки Rental. Додаткові предикати UPDATE/DELETE повторно обмежують статус і пов'язані Rental. Контенція повертає 409 без автоматичного повторення операції. Семантику блокувань описано в [PostgreSQL 18](https://www.postgresql.org/docs/18/explicit-locking.html).

Унікальність і FK забезпечують чинні обмеження PostgreSQL. Repository перетворює Prisma P2002/P2003 та конфлікти P2034/P2025 і SQLSTATE 55P03/40P01/40001 у безпечні `ApiError(409)`; для Prisma 7 SQLSTATE читається також із вкладеної помилки adapter. Непередбачені помилки обробляє наявний middleware як 500. Коди описані в [Prisma error reference](https://www.prisma.io/docs/orm/v7/reference/error-reference).

Майбутній RentalService повинен у транзакції перевіряти неархівовану книгу, блокувати книгу перед примірником у тому самому порядку, перечитувати актуальний статус під блокуванням і лише потім створювати/закривати Rental та змінювати BookCopy.status. CRUD не реалізує ці операції й не змінює Rental/CashMovement. Рядкові блокування захищають паралельні операції, а не застарілі дані форми між двома завершеними запитами; version/ETag у поточній моделі немає.

`scripts/check-book-copies.ts` перевіряє HTTP API у rollback-транзакції, використовує SAVEPOINT для ізоляції SQL-помилок та окремі з'єднання для конкурентних сценаріїв. Ін'єкція connection із runner транзакцій дозволяє гарантовано відкочувати й успішні конкурентні запити. Порівняння повних знімків усіх дев'яти таблиць підтверджує збереження даних. Нових моделей, міграцій чи GoF-патернів не додано.

## Frontend: каталог і примірники

`BooksPage` та `BookDetailsPage` використовують `src/api/books.ts`, спільний `fetch`-клієнт у `client.ts` та типи/перевірки фактичних JSON-відповідей у `book-contract.ts`. Адреса береться лише з наявного `api/config.ts` (`VITE_API_URL` із префіксом `/api`). Каталог використовує серверні `copyCount`, `availableCopyCount` та `pagination`; деталі завантажують книгу й вкладений endpoint примірників. HTTP-, мережеві помилки та некоректні відповіді отримують зрозумілі українські повідомлення; невідома книга має окремий стан 404.

`useApiResource` скасовує запити при зміні залежностей і демонтуванні, ігнорує результати скасованих запитів та одразу приховує дані попереднього запиту. Повторні ефекти StrictMode безпечні. Каталог затримує запит на 300 мс; пошук, сторінка та розмір сторінки зберігаються в query-параметрах React Router. Повернення з деталей зберігає контекст каталогу. Layout змінено лише для активного розділу «Книги» на вкладених маршрутах.

Грошові значення не перетворюються на `number`: `utils/money.ts` форматує валідовані decimal-рядки без арифметики й округлення. Тести на вбудованому `node:test` перевіряють контракт API, статуси, порожні результати, некоректні відповіді та граничні грошові значення. Нових бібліотек, бізнес-правил, доменних класів або GoF-патернів цей етап не вводить; доменні UML-діаграми залишаються актуальними.

## Реалізація чотирьох GoF-патернів

**Strategy.** `DiscountStrategy` з реалізаціями `NoDiscountStrategy` і `PercentageDiscountStrategy`. Відсоток передається як значення з категорії, знімок якого зафіксований у прокаті. **Не** створюємо окремий клас під кожну категорію з БД.

**Observer.** `RentalEventPublisher` поширює `RentalIssued` і `RentalClosed` підписникам (`AuditLogSubscriber`, опціонально `NotificationSubscriber`). `AuditLogSubscriber` додає записи про успішні операції до таблиці `AuditLog`. Події публікуються тільки після успішної транзакції, тому журнал є допоміжним best-effort записом: збій підписника може призвести до відсутності окремого запису, але не повинен відкочувати вже завершений прокат. Достовірні прокати та гроші зберігаються в `Rental` і `CashMovement`. Для гарантій доставки подій у майбутньому потрібен outbox або транзакційний аудит. Журналювання адміністративних змін можна додати пізніше.

**Template Method.** Абстрактний `BaseReport` реалізує фінальний алгоритм `generate(params)` (отримати дані → агрегувати → сформувати результат); конкретні `InventoryReport`, `RentalsReport`, `FinancialReport` реалізують кроки.

**Factory Method.** Абстрактний `ReportCreator` оголошує фабричний метод `createReport()`, який у `InventoryReportCreator`, `RentalsReportCreator`, `FinancialReportCreator` створює конкретні генератори. Це саме GoF Factory Method, не проста функція з `switch`.

## SOLID / GRASP

- SRP: сервіси прокату, розрахунку, звітів мають окрему відповідальність.
- OCP: нові способи розрахунку знижок підтримуються через інтерфейс стратегії; нові типи звітів — через нові генератори/творці.
- DIP: сервіси залежатимуть від контрактів, а не від деталей запитів до БД.
- GRASP: Controller приймає запити, Information Expert зберігає правила там, де знаходяться необхідні дані; High Cohesion, Low Coupling.

## Критичні технічні рішення

- Грошові значення — `Decimal`, не `float`.
- `BookCopy` перевіряємо і змінюємо атомарно разом із видачею.
- Знімки ціни, застави, відсотка і назви категорії читача в `Rental` під час видачі; відсотка штрафу — під час закриття.
- Книги з історією не видаляємо фізично, а архівуємо.
- Backend перевіряє `ADMIN`/`LIBRARIAN`, а не лише frontend.
- Різницю між *нарахуваннями* та *рухом грошей* зберігаємо явно.
- `AuditLog` зберігає історію дій, а не підміняє фінансові транзакції; в записах не дублюємо чутливі дані читачів.

## Розгортання

Frontend і backend запускаються локально окремо та деплояться незалежно, хоча код залишається в одному репозиторії:

- **Frontend** — Vercel, коренева папка проєкту `frontend/`.
- **Backend** — Render Web Service, коренева папка сервісу `backend/`.
- **PostgreSQL** — окрема керована база даних; провайдера оберемо перед деплоєм. Локально — Docker Compose.

Під час початкової ініціалізації створюємо окремі `package.json` та lock-файли для `frontend/` і `backend/`. Поки не використовуємо спільні npm workspaces чи спільну папку пакетів: це спростить незалежні збірки на Vercel і Render. Якщо згодом з'явиться реальна потреба в спільних пакетах, повернемося до цього рішення.

Адреса API передається frontend через `VITE_API_URL`, а рядок підключення БД — тільки backend через `DATABASE_URL`. Backend дозволяє CORS для адреси frontend; секрети не потрапляють до репозиторію або клієнтської збірки. Докладніше — у [плані деплою](deployment.md).
