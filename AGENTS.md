# Правила для Codex — Library Management System

## Мета

Навчальний проєкт з дисципліни «Документування програмного забезпечення та шаблони проєктування» (варіант 20, бібліотека). Перед реалізацією нових задач прочитай `docs/requirements.md`, `docs/business-rules.md` та `docs/architecture.md`.

## Архітектура і стек

- Монорепозиторій з двома незалежними застосунками й власними `package.json` та lock-файлами: `frontend/` і `backend/`.
- `frontend`: React + Vite + TypeScript + Tailwind CSS; у майбутньому деплой на Vercel.
- `backend`: Express + TypeScript + Zod + Prisma; PostgreSQL; у майбутньому деплой на Render.
- Backend: модулі за предметною областю, розподіл controller/service/data access.
- Застосовуй SOLID, не створюй абстракції без користі.
- GoF: Factory Method, Template Method, Strategy, Observer. Реалізовуй відповідно до узгоджених діаграм, а не лише за назвами класів.

## Обсяг змін

- Виконуй **лише поточне конкретне завдання**; не генеруй увесь проєкт одним запитом.
- Не змінюй непов'язані модулі і не проводь великий рефакторинг без прямого прохання.
- Перед складною зміною коротко поясни план і які файли змінюватимеш.
- Наприкінці наведи: змінені файли, що реалізовано, як перевірив, можливі ризики/наступний крок.
- Якщо правила суперечать задачі, вкажи конфлікт і запропонуй найменшу безпечну зміну.

## Якість

- Для грошових сум використовуй Decimal, не JS floating-point arithmetic.
- Видача, закриття прокату, грошові рухи й зміна статусу примірника — транзакційні.
- Зафіксуй ціну, заставу й знижку на момент видачі.
- Backend перевіряє права, валідує запити й повертає зрозумілі помилки.
- Додай тести до нової бізнес-логіки, особливо граничних випадків.
- Ніяких заглушок, які виглядають як робочий функціонал, без явної помітки.
- Не зберігай секрети в Git; зберігай лише `.env.example` без значень секретів.
- Для frontend використовуй `VITE_API_URL` як публічну адресу API; `DATABASE_URL` та інші секрети доступні лише backend.
- Перед деплоєм передбач CORS для конкретного frontend origin і змінні середовища; не хардкодь адреси `localhost`.
- Не додавай конфігурації Vercel/Render та спільні workspaces без відповідної окремої задачі.

## Git

- **Не створюй коміти й не виконуй push без прямого прохання користувача.**
- Коміти мають бути невеликими, змістовними та відповідати реальному прогресу.
- Не додавай у повідомлення коміту `Co-authored-by` чи інші трейлери AI-співавторства.
- Не переписуй історію Git (`reset --hard`, force-push, rebase), якщо про це прямо не просили.

## Документація

- Оновлюй UML і документацію, якщо змінюєш пов'язані бізнес-правила чи структуру класів.
- Пиши зрозумілі імена й коментарі лише там, де вони справді пояснюють логіку.
- Не додавай нові фреймворки / SaaS / зовнішні інтеграції без погодження.

## Розгортання та статус

- Бажана схема: один репозиторій, `frontend/` на Vercel, `backend/` на Render, PostgreSQL — окремо. Поточний стан: лише план; сервіси ще не створені.
- Налаштування хостингу та міграції продакшн-БД виконуватимемо окремим етапом, не на початку ініціалізації.
- Деталі дивись у `docs/deployment.md`.
